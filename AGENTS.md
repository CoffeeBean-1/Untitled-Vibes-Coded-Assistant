## Implementation defaults

Use TypeScript, React, and Vite for the web UI unless the existing repository or an accepted decision requires another stack. Prefer a single small application with feature modules. Add a backend or desktop directory only when that milestone is authorized. Do not create a microservice fleet, a plugin marketplace, a generic block editor, or an AI assistant backend.

Use current supported, mutually compatible dependencies; verify official documentation at installation time and commit the lockfile. Do not trust version numbers in an old plan. Honor an existing package manager. For a new repository, use npm unless workplace policy dictates otherwise. Keep runtime dependencies intentional and record significant additions.

Keep pure domain logic separate from React and from provider SDKs. Use provider/repository interfaces for calendar, task storage, notifications, meeting launch, and optional shell integration. Widgets must share data, not create independent task databases or polling loops.

Use semantic HTML, accessible controls, visible focus, reduced-motion support, and keyboard alternatives for drag and resize. Do not use uploaded HTML, arbitrary CSS, or remote executable widgets. Do not render invitation HTML directly.

Store date-only deadlines as dates, not midnight UTC instants. Store timed deadlines with an instant and intended IANA zone. Use a testable clock, stable IDs, schema migrations, validation at trust boundaries, and explicit failure states.

## Working loop

1. Inspect the actual repository, applicable instructions, Git status, manifests, and existing tests. Do not discard unrelated edits, rewrite history, or run destructive cleanup.
2. Select one bounded backlog work package. State its scope and relevant acceptance IDs. Identify any permission gate before touching a live system.
3. Implement the smallest complete vertical slice. Add tests alongside behavior. Keep demo and live adapters visibly distinct; do not silently fall back to fake live data.
4. Run the available checks and inspect the UI when UI behavior changes. Report unavailable tools as unrun, not passed. Do not open production meetings, place orders, or access work accounts as a test shortcut.
5. Update status, backlog, and decisions. Record exact commands, results, limitations, and the next executable step. End with a short user-facing summary of what changed and what remains blocked.

Do not stop all progress because an optional integration is blocked. Continue with safe demo/core work and record the blocker. Ask only for genuinely material, non-recoverable information or permission. Do not invent permissions or silently choose a paid/hosted service. Do not implement all milestones in one unreviewable change.

## Verification contract

During scaffold, establish real scripts for `npm run dev`, `npm run build`, `npm run typecheck`, `npm run lint`, `npm run test`, and `npm run test:e2e`. `test` must be non-watch in CI. These commands are intended interfaces, not assertions that scripts currently exist.

Use a unit/component runner and a browser E2E runner, with Vitest/Testing Library/Playwright as proposed defaults. Match the repository if it already has a coherent stack. Record exact installed versions and environment.

Before completing a slice, run relevant tests, type checking, linting, build checks, and `git diff --check` when Git is available. Validate responsive sizes, light/dark appearance, keyboard use, loading/empty/error/offline states, and applicable security checks. Never mark a broad milestone complete because a screenshot looks correct.

## Definition of done

The agreed behavior works end to end; acceptance IDs pass with evidence; code is typed and maintainable; access and data handling follow approved policy; failures are actionable; documentation matches implementation; and no placeholder is presented as a working integration. Any incomplete or untested item is explicitly named.

A work-ready release additionally needs the applicable permission gates, tested recovery and reminders, real integration validation on the target machine, performance evidence, and an owner-approved release profile. Optional unavailable features may be deferred only when clearly documented and accepted.
